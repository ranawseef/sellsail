# SellSail SaaS: build plan and handoff

Branch: `feature/saas-app`. Never push to `main`: the owner merges, and Hostinger
auto-deploys `main` (Next.js 16.4.1 standalone under Passenger, Node 22).
Read `CLAUDE.md` and `AGENTS.md` first. This Next 16 has breaking changes:
`middleware` is now `proxy.ts`, so read `node_modules/next/dist/docs` before writing
app code. `cacheComponents` is off. Builds stay on webpack with one worker
(`next.config.ts`) because of Hostinger's process limit.

Do not develop on the Hostinger server itself. Its thread limit is shared with the
live sites, and builds or local databases there crash the session.

## Product

An Amazon → OnBuy dropshipping repricer for UK sellers, now multi-tenant.
AliExpress (source) and eBay (marketplace) come in later phases, and the data
model already allows for them: `source_accounts.source` and
`marketplace_accounts.marketplace`. Show them as "coming soon" in the UI.

## Done on this branch

| Build guard against direct API calls | `scripts/check-egress.mjs` |

| Tests (fixture generated by the original PHP) | `tests/*.test.ts` |

The schema has 19 tables and has been checked against MariaDB 11.8.
`products.needs_push` is a stored generated column: price/stock differ from
what OnBuy last confirmed (`pushed_price`/`pushed_stock`), or `push_requested`
is set. A push records exactly what was confirmed, so a change made mid-push
stays pending.

## First steps

1. Run the tests (`node --test tests/*.test.ts`; Node 22 strips types). They have never completed, so fix anything that fails.
2. In `package.json`: `"build": "node scripts/check-egress.mjs && next build --webpack"`, `"test": "node --test tests/*.test.ts"`.
   Exclude `tests/` from `tsconfig.json` if the `.ts`-extension imports upset `tsc`.

## Remaining MVP

1. **Auth.** Users, tenants and memberships (owner/admin/member). scrypt password hashes. DB sessions storing the sha256 of the token, in an httpOnly SameSite=Lax cookie. Login rate limit via the `rate_limits` table. `tenant_id` always comes from the session, never from client input, and every query filters on it. Write to `audit_log`. On signup, create a tenant with a 14-day trial, default bands (limits 10, 20, 30, 50, 100, 150, 250, 500, 9999) and `repricer_settings`.
2. **Secrets.** AES-256-GCM using `APP_ENCRYPTION_KEY` (32 bytes, base64) for OnBuy keys, the SP-API refresh token and the proxy config. Never log them; mask them in the UI.
3. **Onboarding wizard**, in this order:
   1. Proxy, with an egress IP test (`egressIp`). It comes first because every API call needs it.
   2. OnBuy keys, tested by requesting a token.
   3. Amazon. Either SP-API OAuth (Seller Central consent URL, then the LWA code exchange through the proxy) or a self-authorised client id, secret and refresh token. Several accounts act as shards.
   4. Pricing bands.
   5. Import. Either CSV, or OnBuy `GET /v2/listings` paged while `offset < metadata.total_rows` (limit 500; pages come back short without meaning the end). Skip archived SKUs unless the seller opts in.
4. **Jobs.** A scheduler with DB leases (`jobs` and `job_runs` tables), started in-process from `src/instrumentation.ts`. Also `/api/cron/tick`, protected by `CRON_SECRET`, for a Hostinger cron every minute, because Passenger idles the app.
   - Reprice: 10 batches of 20 ASINs per run via `batches/products/pricing/v0/itemOffers`, paced by `source_accounts.next_allowed_at` (10 s). A per-item 400/404 sets the item out of stock at once; other errors are retried, and after 3 failures the item goes out of stock (price 999, stock 0). Write `price_history` when price or stock changes.
   - Push: up to 1000 `needs_push` rows via `PUT /v2/listings/by-sku` with site_id 2000 and boost. On a 401, renew the token once. Record pushed values only for confirmed SKUs, and archive "does not exist" SKUs.
   - Fair scheduling across tenants; a kill switch (`tenants.paused`); a failing proxy means no traffic and a visible banner.
5. **Stripe billing.** Plans in config: trial, Starter £29, Growth £69, Pro £149, limited by SKU count and number of Amazon accounts. Make the webhook idempotent using `stripe_events`.
6. **UI.** Professional shadcn-style components; `radix-ui`, `motion` and `sonner` are already installed. Match the marketing theme in `globals.css` (sea/sun/paper colours, Bricolage display font).
   - Move the marketing pages into an `app/(marketing)` route group.
   - Add `/login`, `/signup`, and `/app/{overview, products, pricing, automation, connections, billing, settings}`.
   - Animated KPIs, a pipeline view (Amazon → pricing → OnBuy), run history and an error feed.
   - eBay and AliExpress as "coming soon" cards.
7. **Finish.** Run the build, typecheck and tests, then push the branch. Give the owner:
   - the env vars to set in Hostinger: `DATABASE_URL` or `DB_*`, `APP_ENCRYPTION_KEY`, `CRON_SECRET`, `SPAPI_LWA_CLIENT_ID`, `SPAPI_LWA_CLIENT_SECRET`, `SPAPI_APP_ID`, `STRIPE_*`
   - the hPanel cron line.

Never use API keys or credentials from the reference repricer.
